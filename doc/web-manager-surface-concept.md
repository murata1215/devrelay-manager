# web.devrelay.io ― manager 会話サーフェス 構想スペック

> 状態: **v1 構想確定**。devrelay-manager `doc/` に着地（commit 済み）。
> 関連: `doc/council-orchestration-spec.md`（council トグルの挙動はここに従う）
> 改訂: A/B/C 確定 + 切替方式A / backend=managerのみ / 永続化=manager DB を確定。manager サービス化（案A）を明記。

---

## 0. 目的

DevRelay の UI サーフェスを **2面構成**にし、上部の切替ボタンで行き来できるようにする。

- **app.devrelay.io（既存）** = per-project channel UI。Slack 的にプロジェクト＝チャンネルで、`submit → plan → 承認(e/exec) → build` を回す。個別プロジェクトの詳細・監査ビュー。
- **web.devrelay.io（新規）** = manager の会話サーフェス。ChatGPT/Claude web 的な「単一の会話窓」。**複数リポジトリ横断・複数 AI 協議（council）を面倒見るオーケストレーション入口。**

境界:

> **core = 実行 + ガバナンス + 監査（プロジェクト/マシン・スコープ）**
> **manager = 体験 + 多AI協議オーケストレーション + 会話サーフェス（プロジェクト横断）**

manager の存在意義は「複数マシンを跨げないから」ではない（それは core が持つ）。**プロジェクト横断・AI 横断・横断設計のオーケストレーション**という別軸を持つから必要。

---

## 1. 中核原則 ― 「もう一個の Claude Code web UI」にしない

顔は chat でいい。だが中身は chat ではなく **承認付きサイクル**。ここが最大の差別化点であり、外すと "速いだけの UI" に堕ちて governance ポジションが溶ける。

### 1メッセージ = 1ガバナンスサイクル

```
[user] 指示
   ↓
[manager] plan（承認カード）  ← 承認ボタンつき。ここで人間が止められる
   ↓ 承認
[manager] build 進捗
   ↓
[manager] 完了 + devlog リンク
```

app.devrelay.io の `e/exec` テキスト承認を、web では**承認カードの明示ボタン**として表現（等価な governance、UI だけリッチに）。承認ボタン ＝ 現行 MCP の「承認します／実行してください」と等価。

## 2. 【新要件】app.devrelay.io ↔ web.devrelay.io 切替

### 2.1 【確定】切替の実装方式 = **A. サブドメイン分離 SPA**

app.devrelay.io と web.devrelay.io を別 SPA として配信し、トップの切替ボタンは相互リンク。既存 app は完成度が高いので壊さず「隣に建てて相互リンク」＝ minimal-first。app 側の改修は切替ボタン追加のみ。

### 2.2 【確定（要件のみ）】認証・セッション共有

- **要件: app ↔ web を切り替えても再ログイン不要（シームレス）。**
- 実現方式（親ドメイン `.devrelay.io` の共有 Cookie / 共有トークン等）は**実装フェーズで詰める技術詳細**として送り。MCP で既に使っている OAuth の仕組みを流用できる可能性が高い。

### 2.3 切替時に保持したい文脈

- ログイン状態（必須）
- 「いま扱っているプロジェクト（複数可）」の文脈を、app の選択チャンネル ↔ web の横断スレと可能な範囲で引き継ぐ
- ドリルダウン（§7）と対で設計

```
┌───────────────┬─────────────────────────────────────┐
│               │  [app に切替] ボタン    KEISUKE ▾    │ ← トップバー
│  スレッド一覧  ├─────────────────────────────────────┤

│  + 新規スレッド │   ・1メッセージ=1サイクルの吹き出し塊 │
│               │   ・横断スレは per-repo にファンアウト │
```

- **左**: 過去スレッド一覧 + 新規スレッド。

- **右下**: メッセージ入力 + council トグル。
- **下部**: 自分の持ちプロジェクト選択。**複数選択可・未選択でも送信可**（→ §5 の自動発見）。

## 4. 【確定 A】スレッド ↔ プロジェクトのモデル ― **横断スレ、per-repo 実行**

`1プロジェクト = 1リポジトリ`。スレを 1 プロジェクトに縛ると横断設計ができず manager の意義を殺すため、**スレは複数リポジトリを跨げる**。

監査の綺麗さは「ガバナンスの原子を **スレ** ではなく **ビルド** に置く」ことで両立:

| レイヤー | スコープ | 役割 |
|---------|---------|------|
| **スレッド** | 横断（複数リポジトリ・複数 AI） | 会話・設計コンテキスト。横断設計をここで面倒見る |
| **サイクル/ビルド** | **常に単一リポジトリ**（`submit` は 1 projectId） | 承認・実行・devlog はすべて per-repo で残る |

- スレは横断でよいが、**実際に手が入る一手一手は per-repo で承認・記録される**。
- 横断設計は「1 つの設計意図 → 複数 repo への per-repo サブプラン群」として展開し、各 repo のビルド／承認／devlog は独立して残る。
- ＝ **横断 UX と per-repo 監査が同居**する。これが manager の芯。

### 横断ファンアウトの段階（スコープ）

| 段階 | 内容 |
|------|------|
| **v1** | 1 スレ内で、ターン毎に対象 repo を（提案→承認で）切り替えられる。各手は独立した per-repo ビルド |
| **v1.5** | 1 つの設計意図から複数 repo へサブプランをファンアウト。各 repo は独立承認・独立ビルド |
| **v2** | 真の協調的横断（repo 間整合・部分失敗ハンドリングを含む、原子的な横断変更） |

> v2 の「協調的横断」は難所（repo 間整合・部分失敗ロールバック）。v1→v1.5 で「独立 per-repo ビルドの束」から入る。

## 5. 【確定 B】プロジェクト自動決定 = **提案として承認カードに乗せる**

「MCP 経由だと AI がリポジトリを自動決定している」は、ほぼ正しい。正確な実態:

- `submit_instruction` は **projectId が必須パラメータ**。サーバーが探すのではなく、**呼び出し側の LLM が文脈から projectId を決めて渡している**。
- 現行フローでは、投げる前に人間へ「投げ先は◯◯、submit していい？」と**確認**してから submit している。

＝実態は「**AI が自動決定（提案）→ 人間が承認で確定**」であり、"提案に留める" と同一。矛盾しない。

### web.devrelay.io での落とし方

```
プロジェクト未選択で送信（or 複数選択）
   ↓
orchestrator LLM が対象 repo を推定
   ↓
[対象 repo（集合可）+ 選定理由 + 各 repo のサブプラン] を承認カードで提示
   ↓ 承認（訂正可）
per-repo ビルドへ
```

- **最悪ケース = repo 取り違えによる誤爆（別マシンに変更が入る）。** 横断で repo が増えるほどリスク増。routing の提示・訂正可能性は必須。
- 「探す」= 「勝手にやる」ではなく **「提案する」**。承認カードで人間が repo を差し替え・追加・除外できる。

---

## 6. 【確定 C】council トグルと承認の置き場所

- **council トグル**: 入力欄の脇（ChatGPT のモデル切替の位置）。
- **承認**: plan カード内のボタン。現行 MCP の「承認します／実行してください」と等価。
- council ON のスレは、`doc/council-orchestration-spec.md` の「**人間提示は最終1回のみ**」がそのまま承認カードに落ちる。claude↔codex の往復はカード内で畳まれ、人間には収束後の最終 plan が 1 回だけ承認カードとして提示される。

---

## 7. core へのドリルダウン

- web.devrelay.io のスレから「**このプロジェクトで開く**」→ app.devrelay.io の該当 channel へ**ブラウザ遷移**（別 SPA）。
- これは API 呼び出しではなく画面遷移なので、「web フロントは manager のみを叩く（§8.1）」は保たれる。

## 8. manager バックエンド & 永続化

### 8.1 【確定】バックエンド = **manager のみ**

web.devrelay.io のフロントは **manager サービスのみ**を叩く。core API は直接叩かない。

```
web フロント → manager API → (manager が orchestrate) → core（submit/plan/approve/build）→ エージェント
```

### 8.2 【重要】これは manager を "サービス化" する（＝案A / manager v2）

今この会話でオーケストレーションしているのは **MCP クライアント側の LLM（人が操作する Claude）**。web.devrelay.io では、それ（repo 推定 → core に submit → plan 提示 → 承認受けて exec）を **manager 内のサーバーサイド orchestrator LLM** が肩代わりする必要がある。これは memory 上の **「案A：サーバーサイド orchestrator LLM」＝ manager v2** の路線。

> **切替ボタン自体は些末。本丸は manager が「DB + API + サーバーサイド orchestrator」を持つサービスに育つこと。** v1 のスコープはこの前提で引く。

### 8.3 【確定】永続化スキーマ（manager 側 DB・最小案）

横断スレとその per-repo ビルドの紐付けを manager の DB で持つ。最小エンティティ:

| テーブル | 主なカラム | 役割 |
|---------|-----------|------|
| `Thread` | id, title, ownerId, createdAt, updatedAt | 横断スレ本体 |
| `Message` | id, threadId, role(user/manager), content, createdAt | 会話ログ |
| `Dispatch` | id, threadId, messageId, projectId, submissionId, buildId, status, devlogPath, cost, createdAt | **per-repo ビルドへの紐付け＝監査の原子** |

- **1 Thread ↔ N Dispatch（N repo）** が「横断の紐付け」の実体。`Dispatch` が §4 の「ガバナンス原子＝ビルド」に対応。
- 監査線の見せ方 = スレのタイムライン上に各 Dispatch を **per-repo バッジ付き**で並べ、buildId / devlog へリンク。
- **権威データ（実 build・監査ログ）は core に残す。manager DB はそれへの参照（buildId, submissionId, devlogPath）＋スレ文脈だけを持つ**（権威の二重化はしない＝ manager は core を再実装しない原則を維持）。

## 9. v1 minimal ライン（実装スコープ提案）

**v1 に入れる:**
- 左: スレッド一覧 + 新規スレッド
- 右: **横断スレ**の会話ビュー（ターン毎に対象 repo を提案→承認で切替、各手は per-repo ビルド）
- 入力欄 + **council トグル**
- 下部: プロジェクト選択（**複数選択可・未選択 → 候補提示 → 承認**）
- 承認カード: 既存 `submit → plan → 承認 → build` をレンダリング。対象 repo を明示・訂正可能に
- トップに **app ↔ web 切替ボタン**（§2.1 方式 A）
- **manager サービス化の最小形**（§8.2）: サーバーサイド orchestrator LLM + Thread/Message/Dispatch DB + manager API

> **v1 の本当の重さは UI ではなく §8.2 の manager サービス化**。切替ボタン・レイアウトは軽い。

**v1.5 / v2 送り:**
- v1.5: 1 設計意図 → 複数 repo へのサブプラン・ファンアウト（各 repo 独立承認）
- v2: 協調的横断（repo 間整合・部分失敗ハンドリング）、信頼度付き自動確定ルート

## 11. 明示的に「やらないこと」（非スコープ）

- Discord / Telegram / LINE 連携: 既に廃止済み。UI サーフェスは WebUI（PWA + FCM）単独。
- **承認なしの完全自動ルート実行**: v1/v2 通じてやらない。routing も plan と同じく実行前に可視・訂正可能。
- 既存 app.devrelay.io の大改修: 切替方式 A のため、app 側は切替ボタン追加のみ。
- **manager DB での監査データ二重持ち**: 権威は core。manager は参照＋スレ文脈のみ。

## 付記: 位置づけの一文（README / rules 転記候補）

> **app.devrelay.io = プロジェクト個別の実行・監査ビュー（core）。web.devrelay.io = プロジェクト横断の会話サーフェス（manager）。** 横断スレで複数リポジトリ・複数 AI の設計を面倒見つつ、実際の変更は per-repo ビルドとして承認・記録される（横断 UX と per-repo 監査の同居）。web の背後では manager がサーバーサイド orchestrator + 自前 DB を持つサービスとして動き、core の機能は再実装せず参照する。
