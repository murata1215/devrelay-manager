# 2026-08-26 12:29 JST ｜ サイクル1.13: 実LLM結線

## 要求
1.11/1.12 で作った orchestrator LLM 層は `unconfiguredLlm.complete()` が必ず throw し、`POST /threads/:threadId/orchestrate` は常に503を返すだけで draft Dispatch が生まれる経路が存在しなかった。本サイクルは Anthropic 公式 TypeScript SDK を結線し、③ end-to-end（orchestrate → draft → 人間ゲート① → done）を実機で試せる状態にする。ただし遷移表（1.7 ③-1）は無変更、ストリーミング／council結線／コスト集計／④フロント／スモーク実行そのものは非スコープ。

## 実行
- `@anthropic-ai/sdk`（0.120.0）を prod dependency として新規追加（新規npm依存はこれのみ）。
- `apps/server/src/llm/anthropic-llm.ts` を新規作成し、SDKを import するファイルをこの1つに限定。`toLlmCompletion`（text ブロック連結・`stop_reason==='max_tokens'`ならthrow・text皆無でもthrow）、`createAnthropicLlm`（LlmPort実装、model引数をそのままmessages.createへ渡す＝モデル名を一切ハードコードしない）、`anthropicClientFromEnv`（鍵未設定はnull・throwしない）、`describeAnthropicError`（instanceofのみで分類、APIキー値は文言に含めない）を実装。
- `LlmPort`/`LlmCompletion`/`LlmUsage` を `orchestrator-llm.ts` に追加し、`orchestrate()` の戻り値（proposal/conversation双方）に `usage`/`responseModel` を伝搬。`draft-sink.ts` に `inputTokens`/`outputTokens`/`responseModel` を通し、Prisma `Dispatch` に同名3列（nullable）を追加して `prisma migrate dev --name dispatch_llm_usage` を実行（`db push` は不使用）。
- `manager-settings.json`/`.ts` に `llm: { timeoutMs: 60000, maxTokens: 8192 }` を追加し起動時検証対象にした。`routes/orchestrator.ts` は `unconfiguredLlm` を撤去し鍵の遅延シングルトンで実結線、鍵未設定は503（自動フォールバックなし）、副作用のない設定検証を `prisma.message.create()` より前に移して孤児Message行を防止。`index.ts` は鍵の有無のみをログ出力（値は出さない・起動は止めない）。
- 構造テスト（AST＋推移閉包 #99）の禁止フラグメントに `@anthropic-ai/sdk` を追加（6→7点）。合成ソース検出テスト #120 で機械確認。

## 発見
- SDKの `maxRetries` 既定値は **2**、かつ**タイムアウトしたリクエストも既定でリトライされる**ことを公式ドキュメントで確認（参照: https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/typescript のRetries/Timeoutsセクション「Certain errors are automatically retried 2 times by default...408 Request Timeout...are retried by default」「Note that requests that time out are retried twice by default.」／参照日時: 2026-08-26 12:20頃 JST）。「60秒・1回で諦める・自動リトライ無し」という要求を満たすには `new Anthropic({ apiKey, timeout, maxRetries: 0 })` の明示が必須で、これを怠ると要求違反が静かに成立する。
- SDKの `Message.usage`（`Usage`型）の `input_tokens`/`output_tokens` は非nullable。ストリーミング専用の別型 `MessageDeltaUsage` の `input_tokens: number | null` と混同しかけたが、型定義を直接読んで訂正した（実行前に自己修正、`?? 0` フォールバックは不要と判明）。
- `MessagesCreateClient`（テスト差し替え用narrow port）の `create()` を直下に置いた設計は、実SDKクライアントでは `client.messages.create()` である形状差分をtypecheckが検出。`anthropicClientFromEnv` 内で実クライアントを薄くラップして解消（ロジックは持たない委譲のみ）。
