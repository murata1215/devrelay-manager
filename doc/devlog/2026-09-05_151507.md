# 2026-09-05 15:15 JST ｜ サイクル1.29: フェーズ1の残課題修正（送信失敗時の入力保持・web側上限のデッドコード解消）

## 要求

サイクル1.28（テキスト添付フェーズ1）の確認サイクルで判明した2つの実害を修正する。

1. 送信失敗時に本文・添付がクリアされてしまう（貼り直しになる）。
2. web 側 `MAX_TOTAL_TEXT_CHARS = 140_000` が宣言のみでどこからも参照されないデッドコードで、
   140,000文字ガードが server 側でしか効いておらず、送信前にユーザーが気づけない。

マイグレーション `20260905040505_dispatch_attachment` は本サイクル開始前に適用済み（`migrate status` で確認済みとの前提を引き継ぐ）。
本サイクルは web 側のみを対象とし、`apps/server/**` / `prisma/**` には一切触れない。

## 実行

- 新規 `apps/web/src/lib/composer-send.ts`: 「送信を試み、成功ならクリア・失敗なら本文/添付/順序を保持した次状態を返す」
  判断を純関数 `performSend` へ切り出した（web のテストは DOM 無しの `node --import tsx --test` で動くため、
  React コンポーネントを直接テストできない設計上の制約に対応するため）。
  併せて `describeSendError`（例外→表示用1行）、`canFallbackToMessageOnly`（404フォールバック可否）を追加。
- `apps/web/src/lib/attachment.ts`: `WireAttachment` インターフェースを新設してここへ集約
  （従来 `Composer.tsx` 内の `ReturnType<typeof toWireAttachments>[number]` だったものを、
  `composer-send.ts` からも参照できるよう lib 側へ移動）。`combinedTextLength(content, items)` を追加し
  （server `attachment.ts` の同名関数と同じ定義: content.length + 各 text.length の和）、
  `validateAttachments(items, content = '')` に第2引数を追加して合計文字数チェックを末尾に追加した。
  第2引数の既定値 `''` により既存呼び出し・既存15テストは無改変で通る。
- `apps/web/src/components/Composer.tsx`: `handleSend` を `performSend` 呼び出しに差し替え、
  戻り値をそのまま `setContent`/`setAttachments`/`setError` する形にした。`tryAddAttachments` の
  `validateAttachments` 呼び出しにも本文（trim済み）を渡すようにした。
- `apps/web/src/App.tsx`: `handleSend` 内の例外握り潰し（`reportError`）をやめ、送信経路の例外は
  rethrow して呼び出し元（Composer の `performSend`）まで伝播させるようにした。

## 発見・判断

- **添付ありで404（DISPATCH_WORKER_MODE=off）のときの挙動を変更した。**
  - 旧挙動（1.28）: `createMessage` で本文だけ Message として記録し、添付は黙って捨てて
    「（添付は記録されませんでした）」と info 表示。入力欄はクリアされる。
  - 新挙動（1.29）: 添付が1件でもあれば `createMessage` へフォールバックせずエラーとして扱い、
    Message 行を作らずに本文・添付をまるごと保持する（`canFallbackToMessageOnly(status, count)` が
    `404 && count === 0` のときだけ true を返す）。
  - 変更理由: 本サイクルの目的は「送信失敗で入力を失わせない」こと。旧挙動は添付を黙って
    捨てる点で目的と逆行しており、また Message 行を作らないことで保持した内容を再送しても
    二重投稿にならない（Message 行が既にできていた旧挙動では、再送すると本文が二重に記録される
    リスクがあった）。添付が無い場合（count === 0）は失うものが無いため 1.28 の挙動を維持した。
- **web 側 140,000 文字ガード（判断: (a) 実際に効かせる、を採用）。**
  他のクライアント側検証（5MB/10MB/件数10）と一貫させ、送信前に気づける方が良いという
  指示側の推奨を採用。定数の二重管理は、共有 workspace パッケージ新設が tsconfig/vite/
  pnpm-workspace.yaml に波及し本サイクルの規模に対して過大なため見送り、代わりに
  **ドリフト検出テスト（#60）** を追加した: web のテストから server の
  `apps/server/src/orchestrator/attachment.ts` をテキストとして読み、
  `MAX_ATTACHMENT_COUNT`/`MAX_ATTACHMENT_BYTES`/`MAX_TOTAL_ATTACHMENT_BYTES`/`MAX_TOTAL_TEXT_CHARS`
  の4定数値を正規表現で抽出して web 側の値と突合する。server 側の値変更漏れを検出できる
  ことを、コミット前に一時的に server 側の値を書き換えて **実際にテストが落ちることを確認**
  （`MAX_ATTACHMENT_COUNT` を 10→11 に変えて実行 → #60 が `10 !== 11` で fail、
  元に戻して `git status --short` で差分無しを確認）。空振り（常に通るだけの見せかけ）でないことを担保した。
  判定式は server の `combinedTextLength(parsed.data.content, decoded)` と完全一致させた
  （trim 済み本文＋添付全文の合計文字数）。server 側の拒否ロジックはそのまま残す（クライアント側
  チェックはセキュリティ境界ではないため）。原文の切り詰めは引き続き行わない（拒否のみ）。
