- E2E は本サイクルの対象外。実 submit は行わない。
- 完了時、server / web のテスト件数を実測値で報告する。

## 発見・判断

### 「画像を orchestrator LLM に渡さない」制約の担保方法（二重防壁）
1枚目: `buildAttachmentContext` は `kind === 'text'` のものだけを本文へ連結する明示フィルタ。
2枚目（fail-safe）: 画像の `text` は `validateAttachments` の時点で常に `''` に固定される。
万一1枚目のフィルタを書き忘れても、連結対象になるのは空文字であり、**構造的に base64 が
漏れることはあり得ない**。これをテスト #210（`buildAttachmentContext` の返り値に画像の
base64 部分文字列が含まれないことを `assert.equal(result.includes(base64), false)` で
直接検証）で機械的に担保した。

### Prisma スキーマ変更が不要と判断した根拠
`DispatchAttachment.content` は既に `String`（base64 保持）で宣言済み、`draft-sink.ts` /
`dispatch-worker.ts`（`AttachmentReader`）/ `core/submit-args.ts` はいずれも MIME を検査せず
3〜4キーをそのまま転送するのみ。したがって画像対応に必要な変更はすべて manager 側の
バリデーション層（`attachment.ts` 2箇所）に閉じており、`prisma migrate dev` は実行しなかった
（計画どおり）。

### 後方互換の担保方法
`combinedTextLength` / `buildAttachmentContext` の新規パラメータ（`kind`、後者は `mimeType` も）を
オプショナルにする設計にしたことで、1.28〜1.29 時点の既存テスト呼び出し（`kind` を持たない
オブジェクトを渡すもの）を1行も変更せずに型エラー無く通した。画像0件のケースでは
`buildAttachmentContext` が `content` を無改変で返す分岐（`decoded.length === 0`）を維持しており、
テスト #212／既存 #199〜#203（server）・#58〜#60（web）で1.28 との出力同一性を確認した。
