# 2026-08-28 06:37 JST ｜ サイクル1.17: Dispatch プラン取り寄せ API

## 要求
次サイクル④のフロントがゲート②承認カードにプランを表示するため、`GET /dispatch/:id/plan` を追加する。manager DB はプラン本文を持たない（権威は core、manager は submissionId 参照のみ）ため、既存の core 接続経路を再利用して都度取り寄せる読み取り専用の口が要求だった。

## 実行
1.16 と同じ流儀（`dispatch-view.ts` に import ゼロの純粋ロジック、`routes/dispatch.ts` は薄い配線）を踏襲し、`fetchDispatchPlan` / `fetchDispatchPlanHttpStatus` を追加した。core クライアントは worker の pollPlan・既存ゲート②が使う `coreClient.getPlan` をそのまま `gateCore` 経由で再利用し、新規メソッドは足していない。判定順は Dispatch 不在→404、所属 Thread の soft-delete→404、submissionId 無し→409（status 同梱）、core 呼び出し失敗・応答形不正→502、それ以外は core 応答をホワイトリスト整形（status/planMarkdown/summary/executable）して200。`classifyPlanResult` は使わず、`status` をそのまま素通しする実装にした（planning 中も200で返す要求と、kind に潰すと素通し要件を壊すため）。更新系メソッドを deps に一切持たせない設計で副作用ゼロを構造的に保証した。
