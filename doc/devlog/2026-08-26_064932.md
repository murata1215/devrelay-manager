# 2026-08-26 06:49 JST ｜ サイクル1.11: ③-3 orchestrator LLM ＋ governance ＋ tier

## 要求

③の最終段として「人間の曖昧な要求から Dispatch の draft 行を組み立てる orchestrator LLM 層」を実装する。絶対条件は「LLM は draft 行を作るところまで。状態遷移には一切関与させない」を構造として担保すること。加えて (1) instruction 作文＋repo 提案（自己ループ警告付き）、(2) governance テンプレの機械的注入、(3) tier（Heavy/Standard/Light）のルーティング3規則＋Settings JSON によるモデルバインド、(4) コスト取得経路の決定（結線なし）、(5) 新規 npm 依存ゼロでのテスト、を実装する。`doc/orchestrator-layer3-design.md` が権威（spec優先、衝突は記録）。

## 実行

新規モジュール6本（`tier.ts` / `manager-settings.ts` / `governance.ts` / `draft-sink.ts` / `project-proposal.ts` / `orchestrator-llm.ts`）＋ `cost.ts`（型のみ）＋ `routes/orchestrator.ts`（`POST /threads/:threadId/orchestrate`、`DISPATCH_WORKER_MODE !== 'off'` のときのみ登録、`index.ts` へ登録）を追加。`config/manager-settings.json` を新設し tier→model バインドと governance テンプレを1箇所に集約。境界の要は `draft-sink.ts` の `DraftSink`（`createDraft` のみ・`DraftCreateInput` に `status` フィールドが存在しない）で、LLM 層5ファイルは `dispatch-state`/`dispatch-store`/`dispatch-gates`/`dispatch-worker`/`coreClient`/`db/client` を一切 import しない。プロジェクト候補はルート側が `coreClient.listProjects()` で取得しデータとして渡す。tier→model のモデルIDは推測せず、WebFetch で Anthropic 公式ドキュメント（platform.claude.com、2026-08-26時点）を確認し `claude-opus-5`（Heavy）/`claude-sonnet-5`（Standard）/`claude-haiku-4-5-20251001`（Light）を採用した。Prisma に nullable な `tier`/`model` を `Dispatch`・`Message` へ加算するマイグレーション `20260825214634_tier_binding` を実行（既存70件のスキーマ・データに影響なし）。実 LLM クライアントは非スコープのため `routes/orchestrator.ts` の既定アダプタは呼ばれたら明示的に throw する（サイレントなモック応答なし）。

## 発見

① spec §6「選択値は Dispatch と Message に記録」と現行スキーマの差分は、指示スコープ(3)には無かった永続化要求だが spec を優先しマイグレーションで埋めた（指示スコープを超えた判断）。② 実 LLM クライアントの結線は新規依存が必要なため非スコープのまま fail-loud で残した（`unconfiguredLlm` は呼ばれると503相当のエラーになる）。③ `classifyBuildResult` の `failed`/`unknown` 語彙は引き続きサイクル1.10時点で未検証のまま（本サイクルでも実 core スモークは行っていない）。④ building の120分ポーリングバジェットも依然未実測（design doc §12 の該当 open item は本サイクルでは消していない）。⑤ tier モデルIDは記憶に頼らずWebFetchで一次情報を確認してから確定した（spec §6「実装時に現行モデル・価格を確認して確定」への準拠）。
