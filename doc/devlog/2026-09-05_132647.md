# 2026-09-05 13:26 JST ｜ サイクル1.28: チャット入力へのテキスト添付（フェーズ1）

## 要求
core #358 で MCP `submit_instruction` に `attachments`（base64、filename/mimeType/content）が追加され #359 で E2E 済み。manager のチャット入力から core WebUI 同等の貼り付け／ファイル添付を使えるようにする。フェーズ1はテキストのみ（画像はフェーズ2）。添付は指示本文へ展開せず core の attachments へそのまま載せる。

## 実行
実機の core MCP `tools/list` を問い合わせ（読み取りのみ）、上限が「最大10件・1ファイル5MB・合計10MB」であることを確認。永続化は新規 `DispatchAttachment` テーブル（案A）とし、`serializeDispatch` の22キーと4秒ポーリングされる一覧APIには一切乗せない設計にした。migration.sql は手書き（`prisma migrate dev` は不使用）。server 側は純関数 `orchestrator/attachment.ts` を新設し、draft-sink→orchestrator-llm（LLM入力にのみ verbatim 展開・instruction 本文は無変更）→dispatch-worker（submit直前にのみ読む）→submit-args→coreClient まで各層で「非空のときだけキーを足す」形で結線した。Fastify の bodyLimit は既定1MBのままだと base64 膨張（10MB→約13.4MB）で413になるため16MBへ引き上げた。web 側は新規 `lib/attachment.ts`（貼り付け閾値2000文字・連番衝突回避・MIME/ファイル名検証）と `AttachmentChips.tsx`（ProjectPicker と同じチップ/ポップオーバー流儀、読み取り専用プレビュー・先頭2万文字表示＋残数注記）を追加し、`Composer.tsx` に貼り付け/DnD/ファイル選択を結線、`orchestrate-body.ts`/`api.ts`/`App.tsx` まで attachments を通した。`DISPATCH_WORKER_MODE=off` の404フォールバックでは添付を送れないため info 表示に明記した。

## 発見・判断
- MAX_TOTAL_TEXT_CHARS は当初案の400,000ではなく **140,000** を採用した。根拠: 3tier中最小の軽量tier（Haiku 4.5、200,000トークン窓）から出力8,192トークン・システムプロンプト概算10,000トークンを引いた予算181,808トークンに、1文字1トークンという安全側の密度換算（実際は日本語でも1トークンあたり数文字が一般的）を適用し、さらに20%の安全マージンを掛けて切り下げた値。切り詰めは仕様上禁止のため超過時は拒否のみ（server `attachment.ts` 冒頭コメントに全文を記載、web `lib/attachment.ts` はこの値を手動同期）。
- #135（dispatch-view.test.ts のスカラー列挙規則）は「型名が Thread/Message で始まる」という決め打ちから「schema.prisma の `model X` 宣言集合と一致するか」への一般化に置き換え、保護が弱まっていないことをテストで機械確認した。
