# 2026-08-24 23:38 JST ｜ サイクル1.7: ③-1 Dispatch 状態機械 + DB

## 要求
orchestrator ③ 実装の第1段として、「サーバが落ちて再起動しても DB を見れば各 Dispatch が次に何をすべきか一意に決まる」状態にする。Dispatch.status に draft/submitting/stale/approving を追加し、遷移表を1ファイルに一元化、不正遷移は例外化、プロセス内メモリに状態を持たない永続化層とテストを整備する。決定的 worker・orchestrator LLM・governance テンプレ・freshCheck/staleCheck 実処理は非スコープ。

## 実行
着手前に `doc/orchestrator-layer3-design.md`（層③ spec、サイクル1.5確定）を読み、本指示との食い違いを発見：spec §2 line 51 の権威ある状態列挙は10値で `pending` を含まない。実測すると Dispatch テーブルは0行・書き手ゼロだったため、`pending` を11番目の状態として残す選択肢を捨て、default を `draft` に変更し `pending` は値名付きで throw するよう実装した（spec 優先、既存レコード破壊なし＝0行なので無害）。
スキーマに `statusChangedAt`（`updatedAt` は cost/devlogPath 更新でも動くため状態滞在時間の基準に使えない）、`lastPolledAt`（`statusChangedAt` だけだとバックオフ判定に不動点が無い）、`statusReason`（spec §10 no-silent-failure）、`instruction`（無いと `submitting` が再起動後に原理的に再開不能）の4列を追加し、`prisma migrate dev --create-only` で生成したSQLに手動でバックフィルUPDATE文を追記した。
`src/orchestrator/dispatch-state.ts`（純粋・import ゼロ、10状態の遷移表・終端判定・次アクション判定・at-most-once/idempotent区別・不変条件フィールド定義）と `src/orchestrator/dispatch-store.ts`（DB更新前に遷移妥当性と不変条件を検証、`updateMany`のwhereに現在状態を含めた楽観ロック、side-dataを同一UPDATEで書く）を実装した。

## 発見
- `submitting` はクラッシュ後に自動再開できない設計上の穴が判明: `submit_instruction` に冪等キーが無く、core側にも「submission一覧」読み取りAPIが無いため受理有無を照合する手段が無い。孤児 `submitting` 行は必ず `stopped`（自動再試行は重複ビルドを招く）とし、`submitting -> draft` の辺を意図的に作らなかった。core側APIの不足として follow-up 記録。
- `approve_implementation` は `{phase}` のみ返し `buildId` を返さない（`get_build_status` はsubmissionId引数）ため、`building` 状態の不変条件に `buildId` を含めると `approving -> building` が必ず throw する。`requiredFieldsFor('building')` は `submissionId` のみとし、テストで明示的に確認した。
- `failed` と `stopped` を機械的に区別: `failed`=core が実行し否定的結果を報告した（planning/buildingからのみ）、`stopped`=作業が未実行または結果不明（RPC失敗・人間キャンセル・ポーリングバジェット枯渇・クラッシュ孤児）。spec §8「タイムアウトで stopped にしない」は人間ゲート限定で機械ポーリングには適用されないことを遷移表コメントに明記した。
