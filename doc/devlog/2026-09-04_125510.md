## 要求

manager を `manager.devrelay.io → localhost:9026` で公開する準備。core が発行する `Authorization: Bearer <token>`（64桁hex・30日スライディング・Cookie無し）に相乗りする認証を manager に入れ、①core の `GET /api/auth/me` へトークンを転送し許可リストで判定するサーバー側ミドルウェア、②CORS を全開から `CORS_ORIGINS` 明示指定へ締める、③`apps/web/dist` を manager 自身が静的配信する、④web 側でハッシュ経由のトークン受け取り・保持・サインイン/ログアウト UI、を追加する。Caddy 設定（core の TestFlight 機能が自動生成）には触らない。

## 実行

- `apps/server/src/index.ts` に `onRequest` フックを1本追加し、`request.userId`（module augmentation で `FastifyRequest` に追加）に格納。401 `{error:'unauthorized'}`／403 `{error:'forbidden'}`／503 `{error:'auth_upstream_unavailable'}` を返す。既存ルートのロジックは一切変更していない。`MANAGER_AUTH_MODE=off` はローカル開発専用として起動時に警告ログを出す。`MANAGER_ALLOWED_USER_IDS` の件数を起動時にログ出力し、0件なら警告する。

- web 側: 新規 `lib/token-from-hash.ts`（純粋、`#token=<64桁hex>` のみ受理）、新規 `src/auth.ts`（`localStorage['manager_token']` 集約、`clearToken`/`onAuthCleared` 購読、`bootstrapTokenFromHash` は保存後に `history.replaceState` でハッシュを消す）、新規 `components/SignIn.tsx`（「DevRelay でログイン」ボタン1つ、`forbidden` 時は許可されていない旨を表示）。`api.ts` は `request<T>()` 1箇所にのみ `Authorization` ヘッダ付与と 401/403 時の `clearToken` 呼び出しを追加し、エクスポート12関数のシグネチャは変更していない。`VITE_API_BASE` の既定を `'http://127.0.0.1:3100'` から `''`（同一オリジン）に変更し、`apps/web/.env.development` に開発用の値を退避した。`App.tsx` は認証 state・`onAuthCleared` 購読 useEffect・全 hooks 宣言後の early return（`<SignIn>`）・ログアウトボタンのみを追加し、ポーリング `useEffect`（旧 L98-117 相当）と `pollTimerRef` は無改変。

## 発見・注記

- `@fastify/static` は v8 系が Fastify 5 専用（`fastify-plugin: ^5`）で本リポジトリの Fastify 4 とは非互換。npm registry のメタデータで devDependencies の `fastify` 指定を確認し、v7系最終（v7.0.4）を採用した。
- CORS プリフライト（`OPTIONS`）に `Authorization` ヘッダは付かないため、`route-guard.ts` は method が `OPTIONS` のとき常に非保護にしている。ここを見落とすとブラウザからの実クロスオリジン POST が preflight 401 で全滅する。
- ルート保護のプレフィックス許可リスト方式は新規 API 追加時に書き漏れる余地があるため、`route-guard.test.ts` の#178で `routes/*.ts` の実ルート定義を正規表現走査し、「`/health` 以外は必ず `requiresAuth` が true になる」ことを機械確認する回帰テストを追加した（`orchestrator-llm-structure.test.ts` と同じ「新規追加時の抜け漏れ検出」流儀）。
- トークン検証キャッシュは成功のみ・TTL60秒・プロセス内 Map。ログアウト直後に最大60秒だけ manager API が通り得るが、core 側セッションは即削除されるため実害は限定的と判断（設計時の仮定として明記済み）。

## E2E 手順（人間が実施）

1. `apps/server/.env` に `MANAGER_AUTH_MODE=on` / `MANAGER_ALLOWED_USER_IDS=<自分の core user id>` / `CORE_BASE_URL=https://app.devrelay.io` / `PORT=9026` を設定。
2. `pnpm --filter @devrelay-manager/web build` で `apps/web/dist` を生成し、`pnpm --filter @devrelay-manager/server dev`（または `build && start`）を起動。
3. `https://app.devrelay.io` にログイン済みの状態で DevTools コンソールから `localStorage.getItem('token')` を実行し 64桁 hex をコピー。
4. `https://manager.devrelay.io/#token=<コピーした値>` を開く → ハッシュが消え、スレッド一覧が表示されれば成功（Caddy 設定は既存 TestFlight 生成物のまま触らない）。
5. `MANAGER_ALLOWED_USER_IDS` から自分の id を外して再起動 → 「このアカウントは manager の利用を許可されていません」が出れば 403 経路 OK。
6. ヘッダ右の「ログアウト」→ サインイン画面に戻り、リロードしても戻らないこと（`localStorage['manager_token']` が消えていること）を確認。
